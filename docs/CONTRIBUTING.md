# Contributing to Sirius
Contributing to Sirius is a relatively straightforward process.
As this is currently, at large, a solo project, I'm more than happy to accept any contributions (given they're appropriately created and presented).

> **Note**: Sirius currently only supports Linux. WSL has not been tested. There are plans to extend support to the BSDs and Android, then MacOS, and finally Windows. Feel free to work on that as well.

# Setting up a development environment

As one might expect, Sirius has a ton of dependencies, both native libraries and Nim packages.

Sirius expects that you'll use [clang](https://clang.llvm.org/) as the C compiler. `gcc` *might* work, but there are no guarantees for it.

## Building the build system
Sirius uses the `neo` package manager and build system to build itself. You don't need to go and fetch it, you can simply run the following command to bootstrap a development environment for you.

### dependencies required
* libcURL
* OpenSSL
* git

And of course, you must have a working [Nim](https://nim-lang.org) toolchain with [Nimble](https://github.com/nim-lang/nimble) installed. If installed via [choosenim](https://github.com/nim-lang/choosenim), these should be available by default.

### bootstrapping
Run this command:

```sh
./tools/boot.sh
```

It'll do the rest for you, hopefully.

## Getting the native dependencies
Sirius, as of writing this, relies on the following packages you'll need to install via your package manager of choice, in no particular order:
- gmp
- simdutf
- boehmgc/bdwgc
- libcURL
- harfbuzz
- fribidi
- vulkan-loader
- GTK4
- libadwaita
- libx11
- libxcb
- libxcursor
- libxkbcommon
- libxrender

> **Note for Nix users**: You can use the `shell.nix` directly using `nix-shell` which'll handle these for you. A Nix flake would be appreciated. ;)

## Building Sirius
Now, run the following command to compile Sirius:
```sh
./tools/bin/neo build sirius
```

Neo can and will take a minute to fetch all dependencies and verify them at first, but subsequent builds, as expected, will not do the same unless required.

Compilation can take a minute, as Sirius is a relatively larger codebase. Expect the Nim compiler to use around a gigabyte of RAM while compilation occurs, not including the C compiler's memory usage itself.

Now, you should have your very own build of Sirius, alongside a fully working development toolchain for some browser engine hacking! :^)

# Good First Issues
If you're intimidated by the prospect of working on a web engine, you can probably start off small. I'd be more than happy accepting minor contributions fixing warnings, improving the UI, etc.

The scary parts of the engine (IPC, JITs and graphics) mostly don't need to be touched if you're just working on implementing JavaScript functions.

## Implementing Web APIs
Also, if you're trying to implement web APIs: check out Niskriya. It can generate bindings for the JS engine from IDL files (in fact, that's how our `Node`, `Element` and `HTMLElement` types were generated!). It's not a silver bullet, but it's better than manual binding over hours:
```
./tools/bin/neo build niskriya
./niskriya <IDL file> <output file>
```
For now, you're free to contribute the autogenerated stubs too, just to build familiarity.

You can check out [components/scripting](https://git.xtrayambak.xyz/ferus-web/sirius/src/branch/master/components/scripting) for understanding how web APIs are implemented in Sirius. There's not much there yet, but it should give you an idea of how things work, and how the engine handles native objects and JS objects.

## Implementing CSS features
You can find CSS type declarations in [components/css](https://git.xtrayambak.xyz/ferus-web/sirius/src/branch/master/components/css).

The real parser and matching engine lives at [components/style](https://git.xtrayambak.xyz/ferus-web/sirius/src/branch/master/components/style).

The layout calculation code lives at [components/layout](https://git.xtrayambak.xyz/ferus-web/sirius/src/branch/master/components/layout).

This is probably the most simple and underdeveloped part of the entire engine (Sirius is more like a JS engine and web API implementation that happens to have a layout engine attached to it, as of right now :P), so there are plenty of neat low-hanging fruits here.

## Good Practices
Always try to adhere to these, to save both me and yourself some time.

### I'm making any sort of change to the code. 
Make sure your changes will end up compiling properly. This can be done by just compiling Sirius (as in the earlier section) with your patches.

### I'm implementing/stubbing a web API.
Make sure to test the stub or implementation with a bare minimum test in the appropriate subdirectory of `tests/` (or making one if no subdir fits it), and running it with Sirius:
```
./sirius file://tests/path/to/test.html
```

Also, it would be greatly appreciated if you could link to the appropriate sections of what you implemented/stubbed in your merge request description.

### I'm working on layout/CSS.
Again, try browsing some basic sites and test pages with your changes to ensure nothing breaks. A good anchor point would be the Acid1 test (`file://tests/spec/acid1.html`). It's currently horribly broken on Sirius, so any progress towards making it look right would be greatly appreciated too.

### I'm working on the IPC layer, JIT compilers or renderer.
Firstly: awesome! :D

Secondly: Make sure your code works, and isn't standing on a jenga tower of hacks. We already have plenty of those, and I don't want more. :)

# AI Policy
There is no blanket ban on the use of AI for Sirius' development. There is only one requirement: **You must take full responsibility for the code generated by any LLM you use.**

That also means that you must understand what the AI-generated or AI-assisted code is doing. Basically, you must be able to explain it.

That's about it for the AI policy.
